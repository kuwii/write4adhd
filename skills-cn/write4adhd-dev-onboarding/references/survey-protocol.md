# 代码库调查协议

写上手书之前，先摸清这个项目。本文是**调查怎么做**：按什么顺序看、用什么命令、看到什么该记什么、什么时候该停。

调查结论一律写进笔记（`assets/survey-notes-template.md`），笔记放草稿区，不进成品目录。**笔记是写作的唯一素材来源**：写作时只回查笔记 + 少量定点复核，不要边写边重新漫游代码库（那样既烧 token 又会让书的结构跟着漫游路径跑偏）。

## 0. 三条纪律（先记住，违反任何一条都会翻车）

1. **采样，不通读**。大型仓库读不完也不需要读完。永远先 `rg` 定位，再只读命中处上下 30~120 行；不要 `cat` 整个文件。单个文件在一次调查中最多读 2~3 个窗口。
2. **采样控制单点深度，不砍覆盖面**，且边查边记。调查有两条轴（见 `book-blueprint.md` 第 1 节）：脊柱给深度，子系统清单给广度。采样纪律管的是**单个文件读多深**（先 `rg` 后取窗口、每文件 ≤ 3 个窗口），**不是**“脊柱之外的东西可以不看”——清单上每个子系统都至少要一次定点查看（入口 + 核心类名单 + 类头 30 行）；零信息的“存在但不展开”是欠账，不是纪律。
   - **笔记先行**：调查一开始就把模板复制成笔记文件，**每完成一层立刻把该层结论写进去**（write/edit 落盘），不要攒到调查结束凭记忆补。写不出“一句话职责”就说明这层还没看懂——落盘这个动作本身在逼你收敛；中途被打断也不会颗粒无收。
   - **预算按检索次数算**：`read` 和“带检索/取窗口的 `bash`”（`rg`、`sed -n`、`git log`、`wc`……）都算一次，合计 ≤ 90 次（超大仓库放宽到 140）。分层配额：层 1~4 ≤ 30 次，层 5 ≤ 40 次，层 6 ≤ 20 次。超了说明你在某个单点上挖太深——回到清单，**把广度补完比把一口井挖穿有用**。
3. **区分"读到的"和"猜的"**。每条结论都标置信度，笔记里就标，不要等到写作时才回忆：

   | 标记 | 含义 |
   |---|---|
   | ✅ | 读过源码/配置得出的结论 |
   | ▶ | 实际运行过命令、看到过输出 |
   | ⚠️ | 由命名、文档或常识推断，**没读实现** |
   | ❓ | 没搞懂，需要在书里向读者坦白 |

   写作时：⚠️ 要么补验证升级为 ✅/▶，要么在正文里用"看起来是……（我没读到实现）"的措辞；❓ 直接写出来并给查证入口。**任何情况下都不许把 ⚠️/❓ 写成斩钉截铁的陈述句。**

排除范围：`.git/`、构建产物与依赖目录（`target/ build/ dist/ node_modules/ vendor/ .venv/ __pycache__/`）、生成代码（`*_pb2.py`、`generated/`、`target/generated-sources/`）。用 `git ls-files` 而不是 `find` 遍历，天然排除掉大部分。

## 1. 元信息层：这个项目自己怎么介绍自己

先读项目写给人类的文档，性价比最高。

```bash
ls -a                                   # 有哪些顶层文件/目录，一眼看出项目形状
cat README.md                           # 或 README.rst / README.zh.md
ls docs/ && ls docs/*.md | head -30     # 官方文档目录，常有 design doc / architecture 页
cat CONTRIBUTING.md                     # ★ 新人最该读的：怎么构建、怎么测、怎么提 PR
ls .github/ .gitlab-ci.yml 2>/dev/null  # CI 配置：机器替你把关的规则
```

要记下：项目一句话定位、官方文档入口、贡献指南里的构建/测试命令、CI 会跑哪些检查、issue 模板与 `good first issue` 类标签、许可证、发布节奏（`git tag --sort=-creatordate | head -10`）。

⚠️ 文档会过期。凡是准备写进书的命令，都要在第 6 层实测一次；文档与代码冲突时以代码为准，并在书里点出这个冲突（这对新人很有价值："别信 README 那一行，实际上是……"）。

## 2. 形状层：多大、什么语言、怎么分块

```bash
# 文件类型分布（真实源码构成，不含构建产物）
git ls-files | sed 's/.*\.//' | sort | uniq -c | sort -rn | head -20

# 顶层目录各有多少文件：一眼看出重量分布在哪
for d in $(git ls-files | awk -F/ 'NF>1{print $1}' | sort -u); do
  printf '%8d  %s\n' "$(git ls-files "$d" | wc -l)" "$d"
done | sort -rn

# 第二层：把大头目录再切一层，定位真正的核心模块
git ls-files | awk -F/ 'NF>2{print $1"/"$2}' | sort | uniq -c | sort -rn | head -25
```

再读构建配置，搞清模块划分与依赖方向（谁依赖谁 = 分层结构）：`pom.xml` / `build.sbt` / `settings.gradle*` / `package.json`(workspaces) / `pyproject.toml` / `go.work` / `Cargo.toml`(workspace members)。多模块项目里，**模块依赖图就是架构的第一层答案**，值得画进书里。

要记下：主语言与次要语言、代码规模量级（几千 / 几十万 / 上百万行，决定这本书能覆盖多少）、模块列表与一句话职责、哪些目录是核心 / 哪些可以先忽略（测试数据、示例、脚本、文档站、历史遗留）。

**这一层同时产出两张表**（广度轴的地基，字段见 `book-blueprint.md` 第 1.2 节）：

1. **子系统清单**：把模块 + 顶层目录 + 入口归纳成“子系统”粒度（一个子系统 = 读者可能被派去负责的一块，如“调度”“shuffle”“Web UI”“历史回放”“Python API”）。每项记：一句话职责 / 入口 / 核心类 ≤5 / 与脊柱的接口 / 近期改动热度 / 本书篇幅分配。清单要**穷尽**主要子系统——漏掉一个，读者接到的第一个任务就可能在那儿。
2. **模块内部分层**：每个核心模块内部按什么分层（目录 → 层），如 `sql/catalyst` = 解析 / 分析 / 优化 / 计划树；`core` = 调度 / shuffle / 内存 / 存储 / 执行 / UI。看目录名 + 包名就能归纳，不需要读实现。

## 3. 历史层：谁在改、改哪里

```bash
git log --oneline -60                        # 最近的提交在说什么
git log -1 --format='%H %ci'                 # ★ 记下基准 commit，书里要写
# 近半年最活跃的目录 = 项目的"当前战场"
git log --since='6 months ago' --name-only --pretty=format: \
  | grep -v '^$' | awk -F/ 'NF>1{print $1"/"$2} NF==1{print $1}' \
  | sort | uniq -c | sort -rn | head -20
git shortlog -sn --since='1 year ago' | head -15   # 核心团队/主要贡献者
```

要记下：基准 commit、近期活跃区（新人改这里最容易被人 review，也最容易撞车）、commit message 的格式惯例（`[模块] 动词开头` / `feat:` / `Fixes #123`）、发布节奏。

历史层的产出直接喂给两章：`代码库地图`（哪些目录是活的）和`改代码：从构建到 PR`（提交信息怎么写）。

⚠️ **统计口径要诚实**：如果仓库是浅克隆/部分克隆（`git rev-list --count HEAD` 很小，或带 `--filter`），“近半年活跃目录”这类统计的窗口就不是半年。**在书里写明实际口径**（例如：“本书基于一个 100 commit 的浅克隆，活跃度统计窗口是最近 6 天”），别让读者拿它当长期趋势看。

## 4. 入口层：程序从哪里开始动

```bash
# 可执行入口
rg -n --no-heading 'static void main|def main\(|if __name__ ==|func main\(|@SpringBootApplication' \
   -g '!*test*' -g '!*Test*' | head -40
ls bin/ sbin/ cmd/ 2>/dev/null          # 脚本入口，常是用户真正敲的命令
cat <构建文件里的可执行/发布配置>          # 哪个模块被打包成产物
```

三类入口都要找：
- **用户入口**：用户敲的命令 / 调用的 API / 提交的作业（书的第 2、3 章要用）；
- **进程入口**：`main` 函数、守护进程启动脚本（走读 trace 的起点）；
- **扩展入口**：插件/SPI/注册表/配置文件驱动的动态加载（走读时最容易断线的地方，第 5 层要专门处理）。

对库（library）型项目，“入口”就是公共 API 的顶层类型：

```bash
# 顶层包里对外暴露的类型 = 这个项目想让你认识的名词
ls <核心模块>/src/main/<lang路径>/          # 看目录名本身就是概念地图
rg -l '^package ' <核心模块>/src/main | head -20
```

对清单上的**每个子系统**重复一次入口识别（广度轴的定点查看）：它的用户入口/进程入口/扩展入口各是什么、核心类名单（`rg` 找类定义 + 读类头 30 行足够）、以及它和脊柱在哪一跳接上（接不上的写“独立运行，接口是 X”）。每个子系统控制在 2~3 次检索内——这是覆盖承诺的底线成本，不许省。

## 5. 生命线层 ★：端到端走一遍（最重要的一层）

这一层决定这本书有没有用。目标：**挑一个最小的、用户可见的、有意义的操作，把它从入口到结果完整追一遍**，记下每一跳。

选主线的标准：够小（一次调用能讲完）、够典型（走的是核心代码路径而不是特例）、够可见（读者能自己跑出来看到结果）。例：批处理引擎选"读一个文件、做个聚合、打印结果"；Web 服务选"一个 `GET` 请求从路由到响应"；CLI 工具选"最常用的那个子命令"；库选"官方 quickstart 里的那段代码"。

走法：

1. 从入口开始，`rg -n '<符号名>'` 找定义，读定义处的 30~120 行；
2. 记下这一跳：`文件:行` + 一句人话（这一步在干什么）+ 要不要把代码引到书里；
3. 找它调用的下一个关键符号，重复。**8~20 跳就够**，不要一路挖到标准库；
4. 遇到**断线**（异步回调、消息队列、RPC、反射、动态注册、宏/代码生成）不要跳过，把它当成一个知识点记录下来：断在哪、靠什么接上（注册表？配置文件？SPI？事件总线？）。新人 90% 的迷路发生在断线处，**这一段是全书最值钱的内容**；
5. 静态读不通时，**用运行来验证**：加一行日志/打印，重跑那个最小操作，看它到底走了哪条路。这比读十遍代码可靠，而且顺手为第 3 章"先让它跑起来"和第 8 章"调试手段"攒了素材。

要记下：完整的跳表（序号 / 位置 / 人话说明 / 置信度）、所有断线点及接法、这条线上出现的每一个陌生名词（进黑话词典）、哪几段代码最值得引到书里（挑 4~8 段，每段裁到 ≤15 行）。

同时识别**核心抽象**（≤7 个，超过就说明你没抓准）：

```bash
# 被继承/实现最多的类型 = 这个项目的骨架名词
rg -o '(extends|implements)\s+[A-Z]\w+' --no-filename -g '!*test*' \
  | awk '{print $2}' | sort | uniq -c | sort -rn | head -25
# 某个模块里出现频率最高的类型名
rg -o '\b[A-Z][A-Za-z]{3,}\b' --no-filename <核心模块>/src/main \
  | sort | uniq -c | sort -rn | head -40
```

对每个核心抽象记：人话解释、定义在哪个文件、谁创建它、谁消费它、生命周期多长（一次调用 / 一个作业 / 一个进程），以及**职责面**：公共方法按功能分组（列方法签名即可，不读方法体）、它持有谁、谁持有它、内部关键子类/内部类、“哪类需求会落到它身上”。方法签名用 `rg -n '^\s*(def|public|private\[spark\] def) ' <文件> | head -40` 一类命令一次取全再分组——这是建立自顶向下理解最便宜的一步。

## 6. 开发闭环层：新人第二天就要用的东西

**探环境在层 1 之前就做**（它是整个调查的前提，不是走到第 6 层才做的事）：从构建配置推断工具链（`pom.xml`→java/maven、`build.sbt`→sbt、`package.json`→node、`go.mod`→go、`pyproject.toml`→python），`command -v` 逐个探测，把“有/没有/版本”记进笔记第 6 层第一行。缺工具意味着这一层的大部分命令只能标 ⚠️——**这个结论要在调查一开始就定下来**，而不是写到第 3 章才发现自己没法验证任何东西。

这一层的产出几乎原样进书的第 3 章（先让它跑起来）和第 8 章（改代码）。**每条命令都要实测**（标 ▶），实测不了就标 ⚠️ 并说明原因。

要搞清并逐条验证：

- **环境要求**：语言版本、必需的构建工具、需要的外部服务（数据库/容器/JDK 版本）。别只读文档，跑一下 `--version` 确认。
- **怎么构建**：完整构建命令 + **耗时**（第一次 vs 增量，差很多，书里必须写，否则新人会以为卡死了）；能不能只构建自己关心的那个模块（大项目里这是救命信息）。
- **怎么跑测试**：全部测试的命令、**跑单个测试文件/单个用例的命令**（★ 新人最需要的就是这一条）、测试怎么组织（单元/集成/端到端，哪些需要外部服务或很慢）、有没有"提交前必须过"的那一小撮测试。
- **怎么跑一个最小示例**：examples / quickstart 目录里哪个最容易成功；跑出来该看到什么。
- **日志与可观测性**：日志打在哪（stdout / 文件 / 目录）、怎么调日志级别、有没有 UI/dashboard/调试端口。
- **风格与静态检查**：格式化命令、lint/scalastyle/checkstyle/ruff 配置、CI 里会拦什么（本地怎么一次性跑完这些检查）。
- **调试手段**：怎么加日志最快、能不能挂断点（IDE 直接跑？远程调试端口？）、有没有现成的 debug 开关/环境变量。
- **提交流程**：分支命名、commit message 规范、PR 模板、需要签 CLA/DCO 吗、review 节奏、CI 失败去哪看日志。

构建太贵跑不动时的退化方案（大项目常见）：
- 先只构建/测试一个**小模块**，验证工具链是通的；
- 完整构建命令照抄 `CONTRIBUTING.md`/CI 配置，在书里明确标注 ⚠️ 未实测 + 预计耗时 + 出处；
- 用 `dev/`、CI 脚本、`Makefile` 反推真实命令（CI 里跑的就是权威答案）。

## 7. 收尾：把缺口列出来

调查结束前，在笔记里补齐这三张表并做完最后这次核对，它们直接决定书的骨架：

1. **前置知识缺口**：读者画像（初级程序员、本领域零基础）不懂、但脊柱和第 5 层核心抽象里必须用到的概念。每条记：概念 / 为什么需要 / 一句话解释 / 打算放哪一章。放进第 1 章"前置速成"的只留**真的会影响理解主线**的那些（一般 3~6 个），其余在使用处一句话补，或进番外。
2. **坑与警告**：调查中撞到的所有"这里不直观/文档骗人/容易踩"的点。这些是本书的差异化价值，别浪费。
3. **没搞懂的问题**：所有 ❓。写作时逐条决定——补查、或坦白写进书里并给查证入口。
4. **清单覆盖核对**：把子系统清单逐行过一遍，确认每一项在书里的落点（整章 / 巡览一节 / 地图一句话+词典一行）都填了；任何一行空着就是欠账，回去补定点查看。

最后一件事：给这个项目想**一个生活化的核心比喻**（按 `write4adhd-book` 的文风规则），要求它能承载整体架构而不只是一个概念——读者之后每读到一层结构，都能往这个比喻上挂。想不出来说明你对项目的整体形状还没把握，回第 2、5 层再看一眼。
