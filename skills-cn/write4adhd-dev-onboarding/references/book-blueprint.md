# 上手书蓝图

本文规定**写什么**：这本书的骨架、每章必须有什么、代码和命令怎么呈现、以及交付前的上岗清单。

**怎么写**（文风、ADHD 友好规则、HTML/书站制作）不在这里——那是 `write4adhd-book` 的职责，动笔前完整读它的 SKILL.md 和 `references/style-guide.md`、`references/html-craft.md`，本文的规则叠加在它之上。

**先纠正一个容易犯的错误**：祛魅体控制的是**阅读门槛**，不是**知识总量**。读者读完是要成为这个项目某一部分的 owner 的，所以"风格通俗"绝不等于"不求甚解"——该覆盖的子系统、该讲清的结构、该给全的职责面，一样都不能欠账；欠的账用**加章节、分部分**来还，而不是靠删知识把书变短。单个章节内部保持短、保持口语化；全书可以很长。

## 0. 对 write4adhd-book 的五条覆盖

只有这五条不同，其余（段落 ≤ 4 行、每章收束句、术语三步法、软性回顾、人话图注、目录页钩子、导航三件套、Canvas 图表规范、动画不绑架注意力……）**全部照旧继承**。

1. **"点到为止，不讲实现细节" → 要讲实现细节。** 术语三步法的前两步不变（先大白话描述现象，再引出学名 + 英文原文），第三步换成：**把实现落到具体位置**——这个概念定义在哪个文件、谁创建它、谁消费它、它的公共表面长什么样。细节必须绑着代码位置出现，不许悬空讨论。
2. **"不要用另一个技术概念解释技术概念" → 可以用读者已经会的东西。** 读者是初级程序员，他写过的 `for` 循环、用过的 `git`、发过的 HTTP 请求、建过的数据库索引，都是最好的锚点，优先用。但**全书仍然需要一个生活化的核心比喻**承载整体架构（工地、快递分拣中心、餐厅后厨……），技术类比只用在局部机制上。
3. **"篇幅宜短不宜长" → 单页仍然短，全书可以长。** 上岗培训必须覆盖到"能当 owner"，砍内容会砍掉读者吃饭的家伙。所以：**单页的短规则一条不放松**（每页 1~3 节、段落 ≤ 4 行、每页一个收束），全书长度靠**加章节**和**分部分**（见第 2 节）来承载，用分层阅读控制单次阅读负担，而不是靠删减控制总负担。
4. **"数学公式禁令" → 必要时允许。** 项目本身涉及算法/公式（调度、代价模型、机器学习）时可以出现，但每个公式必须紧跟一句人话解释 + 它在代码里的位置（`文件:符号`）。不许出现没有代码落点的纯理论推导。
5. **"不要为了显得通俗而贬低难度" → 坑与警告是一等公民。** 这本书的读者明天就要动这个代码库，"这里很绕""这个配置不生效""这块历史包袱重"是有用信息，不是负面内容。每章该警告就警告，用 `.warn` 框（见 `assets/code-kit.css`）。

## 1. 两条轴：脊柱给深度，清单给广度

### 1.1 脊柱（深度轴）

动笔前先定**脊柱**：一个最小的、用户可见的、有意义的操作，从入口到结果完整走一遍（调查协议第 5 层的产物）。

**走读部分的章节都是这条线上的某一段**：前置速成 = 看懂这条线需要的名词；它是什么 = 这条线为什么值得存在；先跑起来 = 亲手把这条线跑通一次；走读章 = 这条线本身。

定不出脊柱，说明调查没做完，回去补。定出两条以上脊柱，说明这本书该拆成两本——挑一条，另一条降级为巡览章里的重点节。

脊柱在调查里超过 20 跳，说明它天然分两段（"进入引擎之前 / 进入调度之后"之类）——**拆成"走一遍（上）/（下）"两页**，在跨层调用处（如 SQL 层 → Core 层）切分：上页末尾留悬念，下页导语接上。不要硬压成一页，也不要为了省页数砍掉跳数。

同时定下**基准 commit**，写在封面页（"本书基于 `<项目名>` 的 `abc1234`，2026-10-17"）。所有 `文件:行号` 都相对它；这一句话能让读者在行号漂移时不至于怀疑整本书。

### 1.2 子系统清单（广度轴）★

只有脊柱的书是**隧道视野**：读者顺着一条线走到底，抬起头仍然不知道这个项目有哪些房间。而读者下一个任务很可能落在脊柱之外的地方（UI、监控、某个连接器、历史回放……），那时这本书必须已经给过他第一层上下文。

所以调查阶段要产出一张**子系统清单**（调查协议第 2、4 层的产物），覆盖这个项目的**全部**主要子系统，每一项记：

| 字段 | 说明 |
|---|---|
| 名字 | 子系统/模块名 |
| 一句话职责 | 它替谁解决什么问题 |
| 入口 | 用户或代码从哪进（命令 / API / 类 / 配置开关） |
| 核心类 | ≤5 个，含定义位置 |
| 与脊柱的接口 | 在哪一跳接上；独立运行的写"独立运行，接口是 X" |
| 近期改动热度 | 来自历史层统计 |
| 本书篇幅 | 整章 / 巡览一节 / 地图一句话 + 词典一行 |

**覆盖承诺（硬规矩）**：读者未来可能被派到清单上任何一项工作，所以**每一项都至少要有"第一层上下文"**——入口、核心类、和主线的关系、改它的第一站。分配规则：

- 在脊柱上、或用户点名负责的领域 → **整章**；
- 不在脊柱上但真实存在、有人维护 → **巡览章里的一节**（见第 4 节"子系统巡览"）；
- 遗留/冻结/几乎无人改的 → 代码库地图里一句话 + 黑话词典一行，**但这一句话必须包含入口和核心类名**，不许只写"历史遗留，略"。

"存在但不展开"只允许作为**清单上的篇幅标注**，不允许作为零信息的借口。

### 1.3 模块内部分层与核心类职责面（结构轴）

光有目录树和零散代码片段，读者仍然无法自顶向下地想问题。两个补强，都是必选：

- **模块内部分层**：每个核心模块内部是按什么分的层（目录 → 层）。例如某 SQL 模块 = 解析 / 分析 / 优化 / 物理计划 / 算子实现；某核心模块 = 调度 / shuffle / 内存 / 存储 / 执行 / UI。目标是让读者**按目录就能猜代码在哪一层**。
- **核心类职责面**：对每个核心抽象（≤7 个），不只给一句话解释，还要给一张**职责面表**：它的公共方法按功能分组（如"提交作业 / 创建数据 / 配置与状态 / 生命周期 / 广播与累加器"）、它持有谁、谁持有它、**哪类需求会落到它身上**、内部关键子类或内部类。读者要能从这张表回答"我要加的功能，大概率为落在这个类的哪一组方法旁边"。

## 2. 部分（parts）：把长书切成学习阶段

章数超过 ~10 就必须分**部分**。部分 = 读者的学习阶段，也是天然的停顿点（可以分几天读），同时给全书一个能记住的骨架。

默认五部分 + 附录（按项目裁剪，可合并可增删，但顺序遵循"认识 → 地基 → 走读 → 版图 → 干活"）：

| 部分 | 内容 | 读完这部分读者能 |
|---|---|---|
| Ⅰ 认识它 | 它是什么 / **全局形状** / 先让它跑起来 | 说清项目替谁解决什么、机器上实际是什么形状、亲手跑通一次 |
| Ⅱ 地基 | 前置速成 / 代码库地图（含模块内部分层）/ **核心抽象与职责地图** | 看懂任何一章需要的名词；按目录猜代码在哪；说出核心类各自能干什么 |
| Ⅲ 走读 | 脊柱（上/下）/ 硬骨头 | 顺着主线讲清一次调用从入口到结果经过了谁、在哪断线 |
| Ⅳ 版图 | **子系统巡览**（含不在脊柱上但读者可能负责的子系统） | 对脊柱之外的每个子系统有第一层上下文，知道接任务后第一站去哪 |
| Ⅴ 干活 | 改代码：从构建到 PR / 你的第一个改动 / 总结交棒 | 走完一次提交；知道下一步读什么、去哪问人 |
| 附录 | 黑话词典 / 报错与坑对照表 | 速查 |

呈现方式（不需要新组件，用现有设计语言）：

- **目录页按部分分组**：每个部分一个 `<h2><span class="num">Ⅱ</span> 部分标题</h2>` + 一句"读完这部分你能……"，下面挂该部分的 `.toc-item` 卡片；
- **章页 badge 带部分**：`<span class="badge">部分 Ⅱ · 第 5 章</span>`；
- 部分之间不插独立页面（目录页承担分组职责），但每部分的**第一章导语**要软性回顾上一部分（"上一部分你拿到了地图，这一部分开始往里走"）。

## 3. 验收标准：先写"读完你能做到什么"

封面页/目录页要放一张**能力清单**，这是全书的合同，也是你选材的唯一标准——凡是不服务于这张清单的内容，删；清单上勾不到的能力，补章节。

默认清单（按项目类型微调）：

- 用自己的话说清这个项目替谁解决什么问题、在生态里站在哪；
- **画出这个项目的全局形状**：有哪些进程/组件、谁和谁通信、控制流和数据流各走哪、一次作业在拓扑上的路径；
- 在自己机器上把它构建出来、跑通一个最小示例、看到预期输出；
- 说出核心抽象各自的**职责面**（能干什么、持有谁、被谁持有、哪类需求落到它身上），以及它们之间的关系；
- **按目录说出每个核心模块内部的分层**，拿到一个类名能猜出它在哪一层；
- 顺着脊柱讲清一次调用从入口到结果都经过了谁，并指出断线点；
- **对脊柱之外的每个子系统说出第一层上下文**：入口、核心类、和主线的接口、改它的第一站；
- 拿到一个功能需求或一条报错，能在 10 分钟内定位到该看哪个文件；
- 能跑通单个测试、能加断点或日志看到运行时状态；
- 能走完一次提交流程：开分支 → 改 → 过检查 → 提 PR。

## 4. 章节蓝图

一页 = 一章（内容多的章可以拆成两页）。**必选章一个都不能少**，可选章按项目情况取舍。章节归属的部分见第 2 节。

| # | 章 | | 目的 | 必含要素 |
|---|---|---|---|---|
| 0 | 目录页 | 必选 | 让读者知道值不值得读、怎么读 | 书名（说清是哪个项目的上手书）+ 核心比喻副标题 + 基准 commit + 能力清单 + "这本书怎么读"（分层阅读 + 部分结构说明）+ **按部分分组**的目录，每章一句钩子 |
| 1 | 它是什么，凭什么存在 | 必选 | 定位与动机 | 一个真实使用场景（最好是能跑的那段代码/命令）；它替代了什么、痛在哪；在生态里的位置图；与相邻项目的区别（点到为止，不捧不踩）；**核心比喻在这里立起来** |
| 2 | **全局形状：这个项目长什么样** | 必选 | 10 公里高度的系统视图 | 进程/组件拓扑图（谁和谁通信，控制流 vs 数据流两种线）；"什么跑在哪个进程里"表；一次作业在拓扑上走过的路径（不进入代码，只到组件级）；配置、日志、监控这三个横切面各在哪；本地最小形态 vs 集群形态的差异 |
| 3 | 先让它跑起来 | 必选 | 尽早建立"我能让它动"的信心 | 环境要求（含版本）；构建命令 + **预计耗时**；一个最小可跑示例；预期输出（裁剪过）；跑不通时的排查顺序（3~5 条，从最常见开始） |
| 4 | 前置速成 | 必选 | 补领域最小知识 | 3~6 个概念，每个：人话现象 → 学名 → **它在本书哪一章会再出现**；配一张"这些概念之间什么关系"的小图 |
| 5 | 代码库地图 | 必选 | 知道东西在哪、哪些可以先不管 | 目录树（标出核心/可忽略）；每个顶层模块一句话职责；**每个核心模块的内部分层**（目录 → 层）；模块依赖图；"最近哪里最活跃"；规模量级 |
| 6 | **核心抽象与职责地图** | 必选 | 自顶向下的心智模型 | ≤7 个抽象，每个：人话 → 学名 → 定义位置 → **职责面表**（公共方法分组 / 持有谁 / 被谁持有 / 哪类需求落到它 / 内部关键子类）→ 生命周期；一张持有关系图（**推荐分步动画**） |
| 7 | 走一遍（上/下） | 必选（全书重心） | 把静态结构变成动态理解 | 脊柱 trace 的 8~20 跳/页，每跳：`文件:符号` + 一句人话 + 关键片段（≤15 行，带注意力标注）；所有断线点单独讲清怎么接上；一张时序图（**强烈推荐分步动画**） |
| 8 | 挑几块硬骨头 | 可选（1~3 节） | 讲清"改代码最容易碰到"的机制 | 选材标准三选一：改动最频繁的区域 / 新人必踩的坑 / 性能关键路径。每块：为什么难 → 设计取舍 → 代码在哪 → 改它要小心什么 |
| 9 | **子系统巡览** | 必选（1~3 页） | 给脊柱之外的世界第一层上下文 | 清单上没拿整章的子系统，每个一节：它解决什么 / 入口与核心类（带位置）/ 和脊柱的接口 / 改它的第一站；**用户点名的领域若不在脊柱上，必须在这里拿到整章或至少两节**；冻结/遗留子系统也各给一句话（含入口与核心类名） |
| 10 | 改代码：从构建到 PR | 必选 | 打通开发闭环 | 增量构建；**跑单个测试的确切命令**；风格/静态检查一条命令跑完；调试手段（日志开关、断点、远程调试）；分支与 commit message 规范；CI 会检查什么、失败去哪看 |
| 11 | 你的第一个改动 | 必选 | 把知识变成一次提交 | 2~3 个梯度练手任务（改日志文案 → 补一个测试用例 → 修一个小 bug）；找 issue 的路径（标签、入口链接）；从开分支到提 PR 的完整步骤；本地要过哪些检查 |
| ∞ | 总结 + 下一步去哪 | 必选 | 收束与交棒 | 一行公式收束全书；一句读者带得走的话；项目内的进阶材料（design doc、架构文档在哪）；社区入口（邮件列表/论坛/聊天室/issue） |
| 番 | 黑话词典 | 强烈推荐 | 术语速查表 | 表格：术语 / 人话一句话 / 英文原文 / **代码里叫什么（类名、配置项、命令）** / 定义位置。全书出现过的陌生名词都要收进来 |
| 番 | 报错与坑对照表 | 可选 | 救命用 | 表格：报错关键字或现象 / 大概率原因 / 怎么办 / 相关代码位置 |

**顺序上有一个强主张：第 3 章"先让它跑起来"必须在架构讲解之前。** 新人对一个项目建立信任的方式是让它在自己机器上动一次，不是先看架构图。跑起来之后再讲形状、地图和职责面，每个名词都有了落点。

每章的**四件套**（缺一不可）：

1. 页首导语：一句软性回顾 + 一句抛出本页要解决的问题；
2. 至少一张图 **或** 一段带标注的代码（走读章两者都要）；
3. 一个动手任务（`.hands-on` 框）；
4. 页末收束句 + 一个 `.checkpoint` 框（"读完这章你应该能……"，≤3 条）。

**番外速查页（黑话词典、报错对照表）豁免动手任务**——它本身就是一张速查表，再塞任务反而啰嗦；但导语、收束句（或检查点）仍然要有。

**动手任务的梯度**：前几章（前置速成、定位、跑起来之前）尽量用**只读命令**（`git ls-files`、`rg`、`wc -l`、打开某个文件看几行），让没有构建环境的读者也能做；需要构建/运行的任务从第 3 章之后开始，并在任务开头写明前置条件（"做完第 3 章的构建再来"）。全书难度单调递增：看 → 跑 → 改一行看效果 → 补一个测试 → 提 PR。巡览章的动手任务一律只读："打开这个子系统的入口类，找出它的核心类名单"这类。

## 5. 代码引用的规矩

代码是这本书的一等公民，也是最容易失控的地方。硬规矩：

- **前一句人话，后一句指路**：代码块前一句话说明"这段在干什么"，块后一句话说明"注意看哪一行/哪个变量"。不许出现无解说的裸代码块。
- **≤15 行**。超了必须裁剪，删掉的部分用 `// … 省略：这里做 XXX` 占位，让读者知道少了什么、去哪看全文。
- **不许改名**。保留原始标识符、原始缩进、原始注释——读者等会儿要拿这些名字去仓库里搜。
- **必须给出处**：代码块头部标 `路径:起始行号`（`.code-head`）。全书首次出现给完整路径，之后可用短名，但短名要能唯一确定文件。
- **注释翻译不改原文**：原注释是英文或黑话时，在代码块**下方**用人话补一句，不要动源码注释。
- **不做语法高亮**，做**注意力标注**：`.hl` 整行高亮（这一行是关键）、`.mark` 行内重点、`.dim` 先别管的部分。一段代码最多标 2 处——全标等于没标。
- **不搬整个文件、不搬整个配置**。配置文件只引真正影响行为的那几行，其余用省略号。
- **结构类内容优先用表和图，不用代码堆**：职责面、模块分层、持有关系这些信息，一张表/一张图比十段代码片段更能建立自顶向下的理解。代码片段只用在"这一行改变了读者的心智模型"的地方。
- 引到的每一处，交付前回仓库 `rg` 复核一遍（至少抽查 5 处），确认路径存在、行号大致对得上、代码没被你"顺手美化"过。

## 6. 命令与输出的规矩

- **输入和输出分成两个块**：输入块每行以 `$` 开头（`.code-head` 写 `终端`），输出块 `.code-block.out`（`.code-head` 写 `输出（已裁剪）`）。混在一起读者分不清哪些该敲。
- **输出裁剪到刚好能证明"成功了"**，用 `…` 标注省略了多少。
- **耗时命令标预期耗时**：`# 约 8 分钟，第一次会下载依赖`。不写耗时，新人会在第 3 分钟以为卡死并去搜"XXX build hangs"。
- **有副作用的命令先警告**：改全局配置、装东西、删文件、起后台服务——用 `.warn` 框说明它动了什么、怎么撤销。
- **实测优先**：写进书的命令自己跑过（标 ▶）。跑不了的（构建太贵、需要外部服务、需要凭据）照抄 `CONTRIBUTING.md` 或 CI 配置，并在命令旁标 ⚠️ 未实测 + 出处。**绝不把没跑过的命令写得像跑过一样。**
- **⚠️ 只标"项目相关"的命令**。`java -version`、`ls`、`git log` 这类通用工具命令不需要标未实测；要标的是**这个项目特有的**构建/测试/运行命令（`./build/mvn …`、`dev/run-tests …`）——只有它们才可能因项目而异、才需要出处。满页都是 ⚠️ 会把读者淹掉，真正的警告反而没人看。
- 需要环境变量的命令，把变量写在同一行（`FOO=bar cmd`）或单独一行 `export`，不要假设读者的 shell 里已经有了。

## 7. 分层阅读：给读者的两个开关

新人面对陌生项目最容易在"什么都想看懂"里溺水。用分层解决，不靠删内容：

- **可跳过标记**：次要节在标题后挂 `<span class="skip-flag">第一遍可跳过</span>`，目录页说明"标了这个的，第一遍直接跳过，回来查也不迟"。全书标跳过的节 **不超过 1/3**——超过说明主线没抓准。注意：**巡览章的节不标跳过**——它们就是为"读者下一个任务在那儿"准备的，标了跳过等于白写。
- **检查点**：每章末尾 `.checkpoint` 框，3 条以内，写"读完这章你应该能回答/做到什么"。答不上来就是没读懂，回去重读那一节；答得上来就可以放心跳下一章。

另外两个减负手段（沿用 `write4adhd-book`）：**软性回顾**（每章开头一句勾连上一章）和**导航三件套**（读者随时知道读到哪、还剩多少）。

## 8. 图的要求

沿用 `write4adhd-book/references/html-craft.md` 的 Canvas 规范（`setupCanvas` / `setupAnim` / `drawBox` / `drawArrow` / `getColors`、人话图注、亮暗主题都清晰、动画滚出视口自动暂停）。本书至少要有这六张：

1. **生态位置图**（第 1 章）：这个项目在中间，上下游/竞品/它依赖的东西各就位——读者一眼看出"它站在哪"。
2. **全局形状/进程拓扑图**（第 2 章）：组件为节点，**控制流与数据流用两种线**；配"什么跑在哪个进程里"表。这张图是全书的地图底板，后面每章都回指它。
3. **模块地图 + 内部分层**（第 5 章）：核心模块 + 依赖箭头 + 每个模块内部的分层条；标出"你现在只需要看这几个"。
4. **核心抽象持有关系图**（第 6 章）：谁持有谁、谁创建谁。**推荐 `setupAnim` 分步**，一步加一个抽象。
5. **脊柱时序图**（第 7 章）：一次调用在各组件之间的传播。**强烈推荐分步动画**——调用链本质是时间性的，静态图会把顺序信息压扁。
6. **子系统全景图**（第 9 章）：把清单上所有子系统摆进一张图，标出脊柱穿过哪几个、接口在哪——让读者一眼看到"还有哪些房间没进去过"。

Markdown 形态没有 Canvas：退化为 ASCII 图（放围栏代码块里）+ 一句人话图注，或引用项目已有的图片（相对路径，确保在 GitHub 上能显示）。

## 9. Markdown 形态（产物要进项目仓库时）

如果这本书要作为项目文档提交（`docs/onboarding/` 之类），用 Markdown 而不是 HTML：

- 一个目录，`README.md` 当目录页（能力清单 + 分层阅读说明 + 部分结构 + 基准 commit + 章节链接），每章一个文件（`01-what-it-is.md`、`07-trace-1.md`……数字前缀保证顺序，部分用文件名前缀或目录表达均可）；
- 代码块用围栏 + 语言标注，**出处写在块内第一行注释**（`// core/src/main/…/SparkContext.scala:412`）；
- `.callout` → `> **注意**：…` 引用块；`.hands-on` → `> **🔧 动手 5 分钟**` 引用块 + 有序列表；`.warn` → `> ⚠️ **坑**：…`；表格照常用表格；
- 所有链接用相对路径，且能在 GitHub 上点开（引源码用 `../..` 相对路径或完整 commit permalink，别用本地绝对路径）；
- 文风、章节结构、四件套、动手任务、上岗清单**一条不减**——换成 Markdown 只是换载体，不是降低标准。

## 10. 篇幅预算

- 每页正文 ≤ 1200 汉字（英文 ≤ 800 词），**不含代码块与表格**；超了就拆页，别塞。
- 全书 **12~20 页 + 1~2 附录**，分成 **4~6 个部分**。少于 12 页通常意味着广度欠账（对照子系统清单检查）；多于 20 页说明该拆成第二本（比如"进阶：性能与调优"）。
- 代码块全书总量控制在正文量的 1/3 以内。代码多不等于有用——结构信息优先用表和图（见第 5 节），代码只引**能改变读者心智模型**的那几段。
